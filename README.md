# СТО НА ПРИМОРСКОМ

Электронная сервисная книжка автомобиля: клиент видит опубликованную историю обслуживания, администратор ведёт её в панели сервиса.

Сайт: [http://localhost:3000](http://localhost:3000) после запуска. Контакты по умолчанию задаются в `src/lib/config.ts` и могут быть переопределены в разделе «Настройки».

## Что уже работает в коде

- Публичная страница, вход сотрудников и запрос нового пароля через Supabase Auth. Самостоятельной регистрации нет.
- Клиент открывает книжку по персональной ссылке `/book/…`. В базе хранится только хеш токена.
- Роль хранится в таблице `profiles`. Клиент не может назначить себе роль администратора.
- Уже созданные кабинеты клиентов сохранены. Новые клиенты получают ссылку, а не форму регистрации.
- Панель администратора: клиенты, автомобили, заказ-наряд, черновик и публикация, справочник работ, настройки.
- Суммы считаются в копейках. Итог заказ-наряда пересчитывает база, а не браузер.
- Напоминание показывается только если заданы следующий пробег или дата.

Почта, база и файлы заработают после подключения своего проекта Supabase. Пока ключи не заданы, вход сотрудников и персональные ссылки не открывают данные.

## Требования

- Node.js 24
- npm 11
- Проект Supabase с PostgreSQL, Auth и Storage

## Установка и запуск

```bash
npm install
npm run dev
```

Откройте [http://localhost:3000](http://localhost:3000).

Проверка:

```bash
npm run lint
npm run typecheck
npm test
npm run build
```

Продакшен-сборка:

```bash
npm run build
npm start
```

## Переменные окружения

Скопируйте `.env.example` в `.env.local` и подставьте ключи из Supabase → Project Settings → API.

| Переменная | Где используется |
| --- | --- |
| `NEXT_PUBLIC_SUPABASE_URL` | браузер и сервер |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | браузер и сервер, доступ ограничен RLS |
| `SUPABASE_SERVICE_ROLE_KEY` | только сервер и скрипты |
| `NEXT_PUBLIC_SITE_URL` | ссылки в письмах |
| `ADMIN_EMAIL`, `ADMIN_PASSWORD`, `ADMIN_FIRST_NAME`, `ADMIN_LAST_NAME`, `ADMIN_PHONE` | только `npm run create-admin` |
| `ALLOW_DEMO_SEED`, `DEMO_PASSWORD` | только локальный `npm run seed:demo` |

`SUPABASE_SERVICE_ROLE_KEY` не импортируется в клиентские компоненты. Файл `.env.local` не коммитится.

## База данных

1. В Supabase откройте SQL Editor.
2. Если база ещё пустая, выполните `supabase/migrations/20261026000000_init.sql` целиком.
3. Затем выполните `supabase/migrations/20261026010000_access_links.sql`. Эта миграция добавляет персональные ссылки и не удаляет клиентов, автомобили и историю.
4. Убедитесь, что появились таблицы `profiles`, `vehicles`, `service_records`, `access_grants` и бакеты `vehicle-images`, `service-attachments`.
5. В Authentication → Sign In / Providers отключите самостоятельную регистрацию по почте, чтобы аккаунт нельзя было создать в обход интерфейса.

Миграция создаёт справочник из 16 работ, политики RLS и функции сохранения, публикации и отмены заказ-наряда. Она не создаёт администратора и не загружает тестовых клиентов.

Если пользуетесь Supabase CLI, этот файл можно применить командой `supabase db push` из каталога проекта после `supabase link`.

## Первый администратор

В `.env.local` задайте почту и пароль длиной от 12 символов, затем:

```bash
npm run create-admin
```

Скрипт создаёт пользователя через Auth Admin API и записывает роль `admin` ключом service role. Пароль в консоль не печатается. Повторять команду для той же почты можно: роль будет назначена существующему профилю.

Дополнительного администратора назначает тот же скрипт с другой почтой. В интерфейсе кнопки смены роли нет.

## Почта

Регистрация, приглашение и восстановление пароля вызывают настоящие методы Supabase Auth. Приложение не имитирует отправку писем.

В панели Supabase откройте Authentication → Emails и укажите SMTP, когда встроенной отправки недостаточно. В Authentication → URL Configuration добавьте адрес сайта и путь `/auth/callback`.

Если письмо не уходит, администратор может нажать «Создать ссылку» в карточке нового клиента. Ссылка показывается один раз и тоже создаётся Supabase, а не подделывается приложением.

Клиенты не регистрируются. Карточку создаёт администратор, затем в карточке клиента или автомобиля нажимает «Создать ссылку на сервисную книжку». Адрес показывается один раз. Отзыв и перевыпуск делают старую ссылку недействительной.

## Демонстрационные данные

Только локально и только вручную:

```bash
# в .env.local
ALLOW_DEMO_SEED=true
DEMO_PASSWORD=длинный-тестовый-пароль
```

```bash
npm run seed:demo
```

Скрипт не запускается при `NODE_ENV=production` и без `ALLOW_DEMO_SEED=true`. Записи помечены как тестовые. Администратора с известным паролем он не создаёт.

## Роли и доступ

- Клиент читает свои автомобили, свои заметки и только опубликованные записи своих автомобилей.
- Черновик видит администратор. Публикация отдельным действием делает запись видимой клиенту.
- Опубликованную запись нельзя удалить. Её можно исправить или отменить с причиной. Изменения пишутся в `audit_logs`.
- Официальные записи создаются функцией базы `save_service_record`, которая проверяет, что вызывающий — администратор.
- Клиент может только запросить автомобиль. Пока администратор не подтвердит запрос, автомобиль в книжку не попадает.

Проверка в интерфейсе не заменяет RLS: те же ограничения описаны политиками в миграции.

## Напоминания

Внутри кабинета предупреждение появляется, если до назначенного пробега осталось не больше 1000 км или до назначенной даты не больше 14 дней. Если пробег и дата не заданы, дата обслуживания не вычисляется.

Таблица `notification_outbox` подготовлена для будущих email, SMS или push. Отправки из неё нет.

## Установка на телефон

Страница `/install` описывает добавление сайта на экран Android и iPhone. Манифест и значки лежат в приложении, service worker регистрируется в production-сборке и не кэширует кабинеты.

Значки можно пересобрать:

```bash
node scripts/generate-icons.mjs
```
